# 需求分析技能（request-analysis）

## 概述
将模糊需求转化为清晰的技术任务，识别业务影响和技术风险，**主动暴露未知**。

## 触发条件
- 收到新功能需求或变更请求时
- 开启新分支 / 新 Issue 时
- 进入开发 10 阶段流水线的 **Stage 1**

## 前置条件
- 阅读 `.claude/Claude.md` 了解全局红线
- 阅读 `.harness/wiki/领域术语.md` 了解术语
- 与需求提出者沟通到位（或拿到原始需求文档）

## 执行步骤

### Step 1：需求解析
- 提取核心功能点（输入/输出/角色）
- 识别功能边界（什么不做）
- 明确验收标准（可量化）
- **输出**：需求清单（Markdown bullet list）

### Step 2：业务影响分析
- 识别受影响的业务模块 → 映射到 `.harness/wiki/领域术语.md`
- 评估业务流程变更
- 确定用户影响范围（角色 × 操作）
- **输出**：影响模块列表

### Step 3：技术影响分析
- DB 变更需求（新增表 / 字段 / 索引）
- API 变更需求（REST / SSE / WebSocket）
- Agent / RAG / Prompt 变更（影响 `prompt-templates/`）
- 配置 / 环境变量 / 密钥新增
- 监控 / 告警 / 审计的新增
- **输出**：技术变更清单

### Step 4：冲突检测
- 检查与 `.claude/Claude.md` 红线的冲突（重点 R9~R16）
- 检查与 `.harness/rules/ai-special-rules.md` 的冲突
- 检查与现有架构的冲突（依赖倒置、循环依赖）
- **输出**：冲突报告（如有，必须升级到 Owner 决策）

### Step 5：未知列表
- 任何仍不清楚的事实，明确列出"待澄清问题"
- **禁止** 用假设填补 —— 必须问

### Step 6：输出
将以上内容填入 `.harness/changes/{YYYYMMDD}-{feat-name}/summary.md`：

```markdown
# {feat-name} — 需求分析

## 1. 需求描述
（……）

## 2. 验收标准
- [ ] ……

## 3. 业务影响
- 涉及模块：……
- 涉及角色：……

## 4. 技术影响
- DB：……
- API：……
- Agent / Prompt：……
- 配置：……

## 5. 冲突报告
（无 / 如下：……）

## 6. 待澄清问题
1. ……

## 7. Owner
@……
```

## 约束
1. 必须覆盖所有受影响模块，**禁止**遗漏跨模块影响
2. 任何与红线规则的冲突必须**显式**标注，不可跳过
3. 模糊需求必须请求澄清，**禁止**自行假设后推进
4. 单个 summary.md 不超过 300 行；过长则拆分子任务
