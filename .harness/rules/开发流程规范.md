# 开发流程规范

> AI Agent 项目**强制 10 阶段流水线**。每个阶段都有**质量门禁**和**回滚路径**。
> **AI 必须**严格按本流水线推进，不可跳阶段。

---

## 1. 十阶段总览

| # | Stage | 关键动作 | 质量门禁 | 输出物 |
| --- | --- | --- | --- | --- |
| 1 | 需求分析 | 拆解需求、影响分析、冲突检测 | 需求清晰无歧义 | `.harness/changes/{feat}/summary.md` 草案 |
| 2 | 方案设计 | 架构图、API 草表、DB 草表 | 经评审、技术选型有依据 | `summary.md` + 设计文档片段 |
| 3 | 任务拆分 | 工作量估计 ≤ 4h/任务、依赖关系 | 粒度合规、依赖清晰 | 任务清单（Mermaid / GitHub Project） |
| 4 | 编码实现 | 按编码规范编写代码 | ruff / mypy 通过 | git commit |
| 5 | 单元测试 | pytest 覆盖核心逻辑 | **覆盖率 ≥ 80%、核心 100%** | `pytest --cov` 报告 |
| 6 | 代码评审 | Owner + Reviewer 双审 | 0 个 🟥 问题 | 评审记录 |
| 7 | 集成测试 | DB / Redis / 第三方真实联调 | 接口联调通过 | 集成测试报告 |
| 8 | 预发验证 | Staging 跑全链路 | 验证通过 | Staging 验证清单 |
| 9 | 上线部署 | 灰度发布 / 蓝绿 | 冒烟通过 | 部署记录 + Git Tag |
| 10 | 线上观测 | 监控、Trace、Token 用量、错误率 | 业务指标正常 24h | 观测报告 |

## 2. 各阶段详细规范

### Stage 1 — 需求分析（Skill: `request-analysis`）

参考：`.harness/skills/request-analysis/SKILL.md`

必须输出：
1. 需求描述 + 验收标准
2. 业务影响范围（涉及哪些 wiki/术语）
3. 技术影响清单（DB / API / Agent / Prompt / 配置 / 监控）
4. 冲突报告（与红线的冲突）
5. **找不到答案就明确"我不知道"**，禁止脑补

### Stage 2 — 方案设计

- 必须先阅读 `.harness/wiki/架构设计.md` `.harness/wiki/数据模型.md` `.harness/wiki/接口协议.md`
- 涉及多 Agent / RAG / 工作流 → 先看 `.harness/wiki/agent-templates/`
- 设计文档格式见 `docs/进阶开发指南.md`

### Stage 3 — 任务拆分

- 每个任务 ≤ 4 小时
- 明确依赖（DAG）
- 写进 `.harness/changes/{feat}/tasks.md`
- 跨人多任务 → 用 GitHub Project / Jira

### Stage 4 — 编码实现（Skill: `coding-skill`）

参考：`.harness/skills/coding-skill/SKILL.md`

强制约束：
- 单次 AI 变更 ≤ 40% 文件总数
- 不确定就问
- 完成后立即 ruff + mypy + 关联单测

### Stage 5 — 单元测试（Skill: `unit-test-write`）

参考：`.harness/skills/unit-test-write/SKILL.md`

- 新增代码覆盖率 ≥ 80%（`pytest --cov-fail-under=80`）
- 核心链路 100% 覆盖
- LLM 调用必须 mock（respx / pytest-httpserver）

### Stage 6 — 代码评审（Skill: `review-skill`）

参考：`.harness/skills/review-skill/SKILL.md`

- Owner + Reviewer 双审
- 检查项：规范 / 性能 / 安全性 / 可测试性 / AI 红线

### Stage 7 — 集成测试

- 启动 docker-compose（DB / Redis / pgvector）
- 跑 `pytest tests/integration/`
- 真实上传 PDF → 入库 → 检索 → 生成的链路要打通

### Stage 8 — 预发验证（Skill: `deploy-verify`）

参考：`.harness/skills/deploy-verify/SKILL.md`

- Staging 环境用真实 LLM API（生产同款模型）
- 跑 Playwright / curl 走完主路径
- 监控 / Token 用量 / 错误率基线确认

### Stage 9 — 上线部署

- 灰度发布：1% → 10% → 50% → 100%
- 每次扩量前观察 30 分钟
- 触发回滚阈值：错误率 > 1% / P95 延迟 > X ms / Token 配额 > 80%

### Stage 10 — 线上观测

- LangSmith / 自建 OpenTelemetry Trace
- 日 token 用量 / 单次任务成本 / 失败率 / 用户体感延迟
- 每日在群里发日报

## 3. 回滚路线表

| Stage | 回滚策略 | 触发条件 |
| --- | --- | --- |
| 编码实现 | `git checkout -- .` 丢弃变更 | ruff / mypy 编译失败 |
| 单元测试 | 修复测试 或 回退代码 | 测试失败率 > 20% |
| 代码评审 | 重新提 MR | 仍有 🟥 项 |
| 集成测试 | 切到上一个稳定版本 | 接口不通 |
| 预发验证 | 回滚到上一个生产版本 | Staging 异常 |
| 上线部署 | 切流到上一版本镜像 | 冒烟失败 |
| 线上观测 | 紧急回滚 + 模型降级 | 错误率 > 1% / P95 飙升 / Token 超预算 |

## 5. 变更管理目录结构

任何变更必须**先**创建目录：

```
.harness/changes/
└── {YYYYMMDD}-{feat-name}/
    ├── summary.md          # 变更概述（必填）
    ├── design.md           # 设计文档（可选）
    ├── tasks.md            # 任务拆分（必填）
    ├── db-migrations.sql   # 数据库变更（可选）
    └── rollback.sql        # 回滚脚本（可选）
```

> `summary.md` frontmatter 必须包含：
> **状态 / 创建日期 / Owner / TAPD / branch / commit**
> 正文必须包含 **变更概述 / 影响模块 / DB 变更 / API 变更 / Prompt 变更 / 关键约束 / 回滚方案**。

模板见 `.harness/changes/templates/`：
- `summary.template.md` — 变更概述（必填）
- `review.template.md` — 评审记录（合入前必填）
- `tasks.template.md` — 任务拆分（必填）
- `design.template.md` — 方案设计（可选）

## 6. AI 编码约束

### 40% 阈值
- 单次 AI 生成代码变更量不能超过文件总数的 40%
- 超过必须拆分多次操作
- 每次操作后必须 ruff + mypy + 跑相关单测

### 质量检查点（CI 强制）

| Checkpoint | Check Content | Pass Criteria | 对应红线 |
| --- | --- | --- | --- |
| 编译检查 | mypy strict | 0 error | — |
| 规范检查 | ruff lint | 0 violation | — |
| 格式检查 | ruff format | 0 diff | — |
| 测试检查 | pytest --cov | ≥ 80% | **R16** 变更留痕 |
| 评审检查 | review-skill | 0 🟥 issue | **R16** 变更留痕 |
| 红线检查 | scripts/check_red_lines.py | 0 红线 | **R1-R16** |

## 7. 禁止事项

- ❌ 跳过 Stage 1 直接进入编码
- ❌ 多人同时改同一文件未经对齐
- ❌ 上线前未跑预发
- ❌ 监控告警未配置就上线
- ❌ 没有回滚方案就合 MR
- ❌ 涉及 LLM 行为变更无 A/B 评估
